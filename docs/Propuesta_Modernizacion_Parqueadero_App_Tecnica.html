1. Arquitectura y stack

Servicios, tecnologías y comunicación

Monorepo con npm workspaces, sin Nx/Turborepo (no se justifica con 4 servicios en 2 lenguajes). El motor de visión (Python) está desacoplado del motor principal (Node) y se comunican solo por HTTP interno, para que un pico de OCR nunca bloquee la API de negocio.

api
NestJS 10 · Prisma · Node 20

Motor principal. REST /api/v1, JWT + guards de rol, gateway WebSocket, orquesta al vision-engine.

vision-engine
Python 3.11 · FastAPI

Microservicio de OCR/ALPR. Un único endpoint: POST /plate/recognize.

web
React 18 · Vite · TS

Panel de garita (SPA). En prod, build estático servido por Nginx.

movil
Expo · React Native · TS

CampiñaAccess: app de socios (Android/iOS/web), expo-router.

PostgreSQL 16
Prisma ORM

Fuente de verdad. Migraciones versionadas (prisma migrate deploy en el entrypoint).

Redis 7
cache + pub/sub

Cache de zona:{id}:estado y backplane de eventos en tiempo real.

Tiempo real

  • Socket.io, namespace /monitoreo, eventos zona.actualizada, evento.nuevo, alerta.
  • Redis como backplane pub/sub: permite escalar api a varias réplicas sin perder el tiempo real.
  • Elegido sobre SSE por reconexión robusta y soporte de rooms; estándar en el ecosistema NestJS (@nestjs/websockets).

2. Motor de visión y datos

Pipeline de ALPR, modelo de datos y API REST

1Pipeline de reconocimiento (ALPR)

Backend por defecto: fast-alpr — detector yolo-v9-t-384 (ONNX/CPU) + OCR de matrículas cct-xs-v1, ~30 ms por imagen. Se agrega un padding del 12% alrededor del bounding box detectado antes de pasar el recorte al OCR (evita que un detector "corto" trunque caracteres del borde). Si el detector no localiza placa, cae automáticamente a EasyOCR como respaldo; también puede fijarse como backend único con VISION_BACKEND=easyocr. La confianza reportada por fast-plate-ocr llega por carácter y se promedia. Normalización vía regex configurable — soporta formato ecuatoriano (7 caracteres, ej. ABC1234) y colombiano (6 caracteres); umbral OCR_MIN_CONFIDENCE (default 0.35).

EndpointContrato
POST /plate/recognize multipart imagen → { plate_text, confidence, bbox, processing_ms, backend }

3. Seguridad e infraestructura

Autenticación, despliegue y equipos físicos

1Seguridad de la aplicación

  • JWT + guards de rol: ADMIN / OPERADOR / CONSULTA en el panel de garita; SOCIO / STAFF en CampiñaAccess.
  • HTTPS end-to-end: Nginx termina TLS y enruta /api, /uploads, /socket.io a api por red interna.
  • Rate limiting en /auth/login y en los endpoints de /eventos-acceso.
  • Respaldos automáticos: pg_dump programado de Postgres + snapshot del volumen uploads/ (evidencia fotográfica).
  • Auditoría: cada EventoAcceso persiste operador_id, timestamp y resultado — trazabilidad completa de ingresos/salidas.

2Despliegue (Docker)

Cada servicio tiene su Dockerfile multi-stage; docker-compose.prod.yml orquesta el stack completo en una red interna. Único punto expuesto: web (Nginx), que sirve el build de Vite y hace reverse proxy a api. Healthchecks + depends_on: condition: service_healthy evitan enrutar tráfico a un servicio aún no listo. La imagen de vision-engine pre-descarga los modelos ONNX en build time para evitar el retraso del primer arranque.

ServicioImagen base
apinode:20-slim — build TS → solo dist/ + deps de producción
vision-enginepython:3.11-slim (migrable a -cuda + onnxruntime-gpu si el club dispone de GPU)
webbuild Vite → nginx:alpine (estáticos + reverse proxy)

3Equipos físicos e infraestructura de red

Cámaras IP compatibles con RTSP en los dos puntos de acceso (entrada principal y nueva salida trasera), barreras/brazos mecánicos con apertura como evento lógico (un futuro barrera-driver escucha el pub/sub de Redis: evento.nuevo AUTORIZADO → abrir talanquera) y pantallas informativas. Reutilización de equipos existentes del club tras un barrido técnico, con compra/instalación de lo que falte. Fuera de este alcance: postes, suministro eléctrico e internet/red en ambos accesos — infraestructura estructural que provee el club.
